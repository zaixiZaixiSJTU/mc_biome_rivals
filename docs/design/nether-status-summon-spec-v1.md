## 2. 炽足兽：目标、部署与战吼原子顺序

### 2.1 目标集合和选择规则

1. GDD §7.1 的“角色”只包括**英雄与生物**。炽足兽不能选择建筑或结构，即使它们将来可以拥有 FIRE。
2. 合法目标必须由部署者控制、仍在合法区域、仍存活，并且在命令验证时实际带有 `FIRE`。当前原型只给战场对象保存 FIRE，因此现在实际可选的是存活己方生物；将来英雄 FIRE 上线后，己方存活英雄自然进入同一集合，不需要改卡牌文本。
3. 若验证时至少有一个合法目标，部署命令必须选择其中**恰好一个**；漏选、选择未着火对象、敌方对象、建筑、结构、已离场或待死亡对象都在支付前原子拒绝。
4. 若验证时没有合法目标，可以正常部署并支付费用，不创建选择，也不产生移除或治疗事件。不能为了允许空放而接受一个伪目标。
5. 目标在部署命令里随单位格一起提交并锁定，不使用部署完成后的第二条 `pendingChoice`。Unity 必须只高亮合法的世界内角色；无目标时显示“可部署，战吼无目标”，而不是让玩家点击无效对象。

### 2.2 战吼结算顺序

合法部署按以下原子顺序执行：

1. 一次性验证手牌、阶段、费用、目标和单位格；任一失败时不扣费、不移牌、不占格、不推进 revision/实例号，也不发事件。
2. 支付费用、移出手牌、建立炽足兽实例并发布 `CARD_DEPLOYED`；随后执行现有入场光环重算和“有生物召唤/部署”监听。
3. 若部署时没有合法目标，到此结束战吼。若锁定了目标，则在直接效果开始前重新确认它仍在场、存活且仍有 FIRE；前序强制监听使其离场、死亡或已解除 FIRE 时，战吼失效但炽足兽不回手、不退款。
4. 从目标移除**一份且唯一的一份** FIRE，发布 `OBJECT_STATUS_REMOVED(reason = EFFECT_REMOVED)`；将来英雄 FIRE 上线时使用对等的玩家状态移除事件。移除不会结算剩余 FIRE 伤害，也不会保留其剩余持续时间。
5. 只有第 4 步实际移除了 FIRE，才为同一目标恢复 1 点生命，且不超过最大生命。生物发布 `OBJECT_STATS_CHANGED(reason = HEAL)`；英雄发布 `HERO_HEALED`。满生命时实际治疗量为 0，但仍发布治疗结果，表明“成功移除后治疗”已经执行。
6. “移除 FIRE → 治疗”属于同一个直接战吼；由状态移除或治疗引起的监听只在两段直接文本都完成后入队。随后执行统一死亡检查、触发/亡语与胜负检查。治疗不能复活待死亡或已经离场的对象。

本阶段没有“状态被解除时”监听，但事件顺序必须现在固定，避免日后客户端先播放治疗、服务端却先处理解除反应。

## 3. WITHER：创建与完整生命周期

### 3.1 施加条件

1. NT-005 在**主动普通攻击**和作为目标造成的**反击**中都能触发。触发条件是本实例实际对一个生物造成了大于 0 的普通攻击伤害；法术伤害、状态伤害、能力伤害、零攻击和攻击建筑/结构/英雄均不触发。
2. 攻击与反击伤害仍按现有规则同时确定并先发布 `ATTACK_RESOLVED`。随后先处理主动攻击者造成伤害的攻击后监听，再处理反击者造成伤害的攻击后监听。
3. 只对伤害后 `health > 0`、仍在战场的受伤生物施加 WITHER。已经降至 0 的对象不创建无意义状态。施加者即使同时被反击打至 0，只要它已造成合法伤害且目标仍存活，其攻击后效果仍会结算。
4. 状态施加完成后才执行该次攻击的统一死亡检查。因此两只存活的 NT-005 互相伤害时，双方均可获得 WITHER；一方死亡时只给存活的一方施加。

### 3.2 数值、刷新和来源

- `WITHER` 每次在受影响对象控制者的结束阶段造成 **1 点真实伤害**，默认持续 **2 次该控制者的结束阶段**。
- 同名 WITHER 不叠加，不会因多个来源每阶段造成多次伤害。再次施加时，剩余次数取 `max(当前剩余次数, 2)`。
- 刷新使剩余次数实际增加时，来源元数据替换为本次施加者的 `playerId/cardId/instanceId/effectId`；在剩余次数已经为 2 时再次施加只发布当前结果，持续时间和既有来源不变。这与现有 FIRE/POISON 的确定性来源规则一致。
- NT-005 使用 `effect.nt_005.01`。状态来源实例以后离场、死亡或变形不移除 WITHER；快照仍保存施加时的来源字段。
- GDD 允许 WITHER 作用于英雄与生物，但 NT-005 只会指定生物。RULE-032C/D 只需上线**战场生物**的 WITHER 协议与结算；英雄 WITHER 留给首张明确施加英雄凋零的卡牌，不借本任务扩张玩家状态模型。

### 3.3 结束阶段结算、击杀与终局

1. WITHER 与现有对象状态在“回合结束效果”之后的状态窗口结算。战场对象按逻辑格索引升序、再按实例 ID 排序；同一对象上的多个状态按权威状态数组顺序结算。刷新不改变该状态在数组中的位置。当前原型用稳定顺序替代 GDD §17.2 尚未提供 UI/命令的玩家自选排序。
2. 轮到 WITHER 时，先造成 1 点真实伤害并发布 `OBJECT_STATS_CHANGED(reason = DAMAGE, damageType = TRUE)`，事件携带已保存的状态来源。
3. 若对象仍存活，剩余次数减 1：大于 0 时发布 `OBJECT_STATUS_TICKED`；等于 0 时移除并发布 `OBJECT_STATUS_REMOVED(reason = DURATION_EXPIRED)`。
4. 若伤害致死，立即以保存的 `sourcePlayerId` 建立击杀归属并执行死亡、亡语与掉落；死亡对象随离场清空状态，不再额外发布该 WITHER 的 TICKED/REMOVED。敌方施加者即使已离场，掉落仍归其玩家。
5. 每个致死状态片段完整结算后重新检查对局。若亡语或相关链路令英雄生命归零并结束比赛，立即停止后续对象、后续状态、下界要塞和回合移交；最终事件不得出现在 `MATCH_ENDED` 之后。

## 4. 下界要塞：支付与召唤事务

### 4.1 触发窗口与多实例顺序

1. 下界要塞在控制者的结束阶段“回合结束效果”窗口触发。为保持 RULE-031 已上线顺序，窗口固定为：海底神殿等既有效果 → 僵尸猪灵岩浆（单位格/实例 ID）→ **下界要塞岩浆** → 对象状态。也就是说，猪灵可以先消耗最后一点红石，之后要塞会因能量不足跳过。
2. 进入要塞子窗口时，对所有存活、在场且效果已实现的 NT-008 建立稳定快照，按其**起始建筑格索引升序、再按实例 ID**逐座结算。结构占据三格但只触发一次。
3. 每座轮到时重新确认来源仍在场且存活，并重新读取当前可用红石与当前单位格；不得复用上一座的检查结果。标准原野通常只能容纳一座三格要塞，但该规则也覆盖其他场地或未来效果产生的多实例。

### 4.2 单座要塞的原子事务

每座要塞按以下顺序处理：

1. 若对局已结束、来源失效、总可用红石少于 1，或没有空单位格，直接跳过；不扣费、不推进实例号、不发空资源/召唤事件。
2. 选定当前从左到右第一个空单位格。格序使用逻辑 `U1 → Un`，不使用 2.5D 世界坐标或屏幕位置。
3. 原子消费 1 点红石，继续复用统一支付规则：先扣临时红石，不足部分才扣基础红石；随后发布 `REDSTONE_CHANGED(reason = AUTOMATIC_PAYMENT, sourceCardId = nt_008, effectId = effect.nt_008.01)`。
4. 紧接着在已选格创建 TK-015 并发布 `OBJECT_SUMMONED`，事件携带要塞的卡牌/实例/效果来源和令牌最终属性、格位及新实例号。支付成功后若内部召唤不能完成，整个权威命令必须失败回滚，不能接受“扣费但无令牌”的部分状态。
5. 结算新单位引发的光环、召唤监听、状态和统一死亡/胜负检查，再进入下一座要塞。TK-015 视为本回合召唤、默认不能立即攻击，也没有战吼或 WITHER 能力。
6. 前一座占用最后空格后，后一座重新检查会满场跳过且不扣费；若仍有空格，后一座使用新的最左空格。任一召唤后的强制链路结束比赛时，停止剩余实例与阶段步骤。
