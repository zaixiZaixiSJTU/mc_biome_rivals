# Nakama Server Module

`src/rules` 是纯规则核心；`src/matches` 和 `src/rpc` 是 Nakama 边界适配器。构建产物只有 `build/index.js`，供 Docker 容器加载。

先后手由可回放的对局种子决定，不依赖玩家进入房间的先后顺序。

当前实现工程闭环需要的 30 张牌库、先手 3 张/后手 4 张起手、双方各一次任意数量调度、首回合抽牌、7 张手牌上限、公开爆牌、递增真实疲劳、开局快照、卡牌部署、主行动/战斗阶段、普通攻击、同步反击、死亡离场、英雄伤害/护甲、胜负、结束回合和认输。调度时先暂时移出所选卡、抽取等量替换牌，再把原牌洗回隐藏牌库；双方确认前权威状态保持 `MULLIGAN`，普通对局命令不会生效。稳定 `effectId` 注册表现已接入 8 个效果：`蜜蜂`战吼治疗、`沙尘暴`全场生物伤害、`熔岩献祭`、`雪球`、`腐肉`、`骨头`友方临时增攻、`圆石`建筑治疗和`潜影壳`。目标会在付款前按敌我关系、对象类型和稳定实例 ID 校验；临时增减攻由权威状态记录并在施法者回合结束时通过独立事件恢复。基础关键词 `TAUNT` 与 `CHARGE` 已成为公开战场状态：多个存活嘲讽目标会共同屏蔽英雄和非嘲讽对象，冲锋允许生物在召唤回合攻击。其余效果会在支付费用前明确拒绝。战场格保存稳定实例 ID，多格结构的多个格子引用同一个状态对象。抽牌和调度事件按接收玩家单独投影，对手只能看到未知手牌位与区域数量；完整牌库顺序不离开服务端。当前 74 张机制验证卡不足以组成满足同名上限的完整单阵营牌组，因此匹配初始化暂用 30 张可复现的群系测试牌序；构筑校验仍待接入。当前卡池已有 4 张嘲讽牌，但还没有正式冲锋卡牌；不可指定状态与其余具体卡牌效果仍待实现。新增规则时先写规则测试，再接 Match Handler，避免把领域逻辑写进网络回调。

两名客户端加入 Nakama matchmaker 时必须通过字符串属性 `factionId` 提交七个已注册群系之一。`biomeRivalsMatchmakerMatched` 会校验人数、用户 ID 与群系值，并把用户到群系的映射传入 `nk.matchCreate('biome_rivals')`，确保返回的是权威 Match Handler，而不是同名中继房间。Match Handler 按该映射建立可复现的群系测试牌序，不能根据连接先后猜测玩家阵营。

协议 opcode：`1` 命令、`2` 事件批次、`3` 命令拒绝、`4` 权威快照。协议结构以 `shared-schema/protocol` 为准。

当前基础对局纵向切片使用 `protocolVersion: 8` 与 `rulesetVersion: prototype-0.9`。v2 将战场格内容从卡牌 ID 改为稳定实例 ID；v3 加入私有牌库、抽牌、爆牌与疲劳状态；v4 加入权威 `PLAY_CARD` 与英雄效果事件；v5 加入目标实例与临时属性变更/恢复事件；v6 在双方公开状态中加入服务器确认的 `factionId`；v7 加入私有 `MULLIGAN` 命令、公开准备状态与正式开局事件；v8 将 `TAUNT`、`CHARGE` 关键词随部署事件和快照公开同步。`prototype-0.9` 增加召唤回合的冲锋例外与嘲讽强制目标过滤。旧规则集客户端不能静默兼容。

运行：

```powershell
npm test
npm run build
```
